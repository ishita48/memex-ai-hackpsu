1. PROJECT OVERVIEW
================================================================================

Memex AI is an AI-powered incident intelligence system that turns logs, errors,
and events into searchable, clustered, actionable memory.

Core value proposition:
"Every company collects logs. Nobody can search them by meaning. We fix that."

One-liner pitch:
"Today Sentry tells you an error happened. We tell you WHEN it happened before,
HOW it was fixed, and WHICH commit resolved it. That's the difference between
observability and intelligence."

What it does:
- Ingest: Accept logs via paste, structured form, file upload (JSON/CSV/TXT), or API
- Embed: Convert text to vectors using OpenAI text-embedding-3-small
- Store: Save in Supabase PostgreSQL with pgvector extension
- Search: Hybrid search (vector cosine similarity + keyword matching)
- Reason: GPT-4o-mini analyzes results and explains root cause, impact, fix, pattern
- Cluster: Automatically group similar events into incidents
- Alert: Auto-fire alerts for critical/high severity events
- Feedback: Users rate results as helpful/not helpful, improving future rankings
- Rerank: Results boosted by feedback score + recency decay

Three sponsor modes (same backend, different data types):
- Sentry mode → errors (NullPointerException, timeouts, memory leaks)
- Comcast mode → network events (bandwidth spikes, latency, DNS failures)
- Base44 mode → API/infra events (schema rollbacks, deploy failures, OOMKills)

3. ARCHITECTURE
================================================================================

User → Next.js Dashboard → API Routes → Memory Engine → Supabase (pgvector)
                                ↓
                             OpenAI
                          (embeddings + reasoning)

INGEST FLOW:
1. User submits log (paste/form/file/API)
2. POST /api/ingest
3. lib/memory.ts → embed(content) → OpenAI embedding
4. find_similar_memory() → check if similar event exists (threshold 0.82)
5. If similar → reuse incident_id (cluster into existing incident)
6. If new → create new incident in incidents table
7. Insert memory with embedding + incident_id
8. If severity = critical/high → create alert in alerts table
9. Return { id, incident_id, is_new_incident, alert_triggered }

QUERY FLOW:
1. User types question
2. POST /api/query
3. lib/memory.ts → embed(question) → OpenAI embedding
4. match_memories_hybrid() → vector search + keyword search combined
5. Rerank results by: similarity + feedback_score boost + recency decay
6. Pass top 5 results to GPT-4o-mini for structured reasoning
7. Check for pattern (multiple incidents in results)
8. Return { results, reasoning, pattern }

BROWSE FLOW:
1. User presses Enter with empty query
2. POST /api/query (no question)
3. lib/memory.ts → browse() → simple SELECT ordered by created_at
4. Return results without reasoning

5. DATABASE SCHEMA (SUPABASE SQL — V2)
================================================================================

NOTE: Run these one at a time in Supabase SQL Editor, or all at once using
"Run" (NOT "Explain").

--- FULL SQL (run as one block) ---

create extension if not exists vector;

drop table if exists alerts cascade;
drop table if exists memories cascade;
drop table if exists incidents cascade;

create table memories (
  id uuid primary key default gen_random_uuid(),
  type text not null,
  source text not null,
  content text not null,
  metadata jsonb default '{}',
  embedding vector(1536),
  incident_id uuid,
  feedback_score int default 0,
  resolved boolean default false,
  resolved_at timestamptz,
  resolved_by text,
  created_at timestamptz default now()
);

create table incidents (
  id uuid primary key default gen_random_uuid(),
  type text not null,
  title text,
  severity text default 'medium',
  status text default 'open',
  event_count int default 1,
  first_seen timestamptz default now(),
  last_seen timestamptz default now(),
  root_cause text,
  fix text,
  metadata jsonb default '{}'
);

create table alerts (
  id uuid primary key default gen_random_uuid(),
  incident_id uuid references incidents(id),
  memory_id uuid references memories(id),
  severity text not null,
  title text not null,
  message text,
  acknowledged boolean default false,
  created_at timestamptz default now()
);

create index if not exists memories_embedding_idx on memories using ivfflat (embedding vector_cosine_ops) with (lists = 100);
create index if not exists memories_type_idx on memories(type);
create index if not exists memories_incident_idx on memories(incident_id);
create index if not exists memories_created_idx on memories(created_at desc);
create index if not exists incidents_status_idx on incidents(status);
create index if not exists alerts_ack_idx on alerts(acknowledged);

create or replace function match_memories_hybrid(
  query_embedding vector(1536),
  query_text text,
  match_threshold float,
  match_count int,
  filter_type text
)
returns table (
  id uuid, type text, source text, content text, metadata jsonb,
  incident_id uuid, feedback_score int, resolved boolean,
  created_at timestamptz, similarity float
)
language sql stable
as $$
  select
    m.id, m.type, m.source, m.content, m.metadata,
    m.incident_id, m.feedback_score, m.resolved, m.created_at,
    greatest(
      1 - (m.embedding <=> query_embedding),
      case
        when m.content ilike '%' || query_text || '%' then 0.5
        when m.metadata::text ilike '%' || query_text || '%' then 0.4
        else 0
      end
    ) as similarity
  from memories m
  where m.type = filter_type
    and (
      1 - (m.embedding <=> query_embedding) > match_threshold
      or m.content ilike '%' || query_text || '%'
      or m.metadata::text ilike '%' || query_text || '%'
    )
  order by similarity desc
  limit match_count;
$$;

create or replace function find_similar_memory(
  query_embedding vector(1536),
  similarity_threshold float,
  filter_type text
)
returns table (id uuid, incident_id uuid, similarity float)
language sql stable
as $$
  select m.id, m.incident_id, 1 - (m.embedding <=> query_embedding) as similarity
  from memories m
  where m.type = filter_type
    and m.incident_id is not null
    and 1 - (m.embedding <=> query_embedding) > similarity_threshold
  order by m.embedding <=> query_embedding
  limit 1;
$$;

create or replace function get_incidents(
  filter_type text,
  filter_status text default null,
  result_limit int default 20
)
returns table (
  id uuid, type text, title text, severity text, status text,
  event_count bigint, first_seen timestamptz, last_seen timestamptz,
  root_cause text, fix text, metadata jsonb
)
language sql stable
as $$
  select
    i.id, i.type, i.title, i.severity, i.status,
    count(m.id) as event_count,
    i.first_seen, i.last_seen, i.root_cause, i.fix, i.metadata
  from incidents i
  left join memories m on m.incident_id = i.id
  where i.type = filter_type
    and (filter_status is null or i.status = filter_status)
  group by i.id
  order by i.last_seen desc
  limit result_limit;
$$;

6. CORE ENGINE (lib/memory.ts) — KEY FUNCTIONS
================================================================================

embed(text) → number[]
  - Calls OpenAI text-embedding-3-small
  - Returns 1536-dimension vector

ingest(entry) → IngestResult
  - Embeds content
  - Checks for similar existing memory (threshold 0.82)
  - If similar → reuses incident_id (clustering)
  - If new → creates incident in incidents table
  - Inserts memory with embedding
  - Fires alert if severity is critical/high
  - Returns { id, incident_id, is_new_incident, alert_triggered }

query(question, mode, matchCount=10, threshold=0.25) → QueryResult
  - Embeds question
  - Calls match_memories_hybrid (vector + keyword)
  - Reranks by: similarity + feedback boost + recency decay
  - Sends top 5 to GPT-4o-mini for structured reasoning
  - Checks for incident patterns across results
  - Returns { results, reasoning, pattern }

browse(type, limit=20) → Memory[]
  - Simple SELECT from memories filtered by type
  - Ordered by created_at DESC

getIncidents(mode, status?) → Incident[]
  - Calls get_incidents SQL function
  - Returns grouped incidents with event counts

getIncidentMemories(incidentId) → Memory[]
  - All memories linked to a specific incident

updateIncidentStatus(incidentId, status, rootCause?, fix?)
  - Updates incident status (open/investigating/resolved)

submitFeedback(memoryId, delta)
  - Increments/decrements feedback_score on a memory

getAlerts(acknowledged?) → Alert[]
  - Lists alerts, optionally filtered by acknowledged status

acknowledgeAlert(alertId)
  - Marks alert as acknowledged

resolveMemory(memoryId, resolvedBy?)
  - Marks memory as resolved with timestamp

7. API ROUTES
================================================================================

POST /api/ingest
  Body: { type, source, content, metadata }
  Returns: { success, id, incident_id, is_new_incident, alert_triggered, message }

POST /api/query
  Body: { question, mode }
  Returns: { results, reasoning, pattern }
  If question is empty: returns browse results (no reasoning)

GET /api/incidents?mode=sentry&status=open
  Returns: { incidents }
GET /api/incidents?id=<uuid>
  Returns: { memories } (all memories for that incident)
PATCH /api/incidents
  Body: { id, status, root_cause?, fix? }
  Returns: { success }

POST /api/feedback
  Body: { memory_id, action } (action = "helpful" | "not_helpful" | "resolve")
  Returns: { success }

GET /api/alerts?unread=true
  Returns: { alerts }
PATCH /api/alerts
  Body: { id }
  Returns: { success }

14. BRUTAL WEAKNESSES IDENTIFIED
================================================================================

1. Reactive not proactive — waits for user to search instead of alerting intelligently
2. AI reasoning is generic — any team can pass results to GPT, no structured chain
3. No temporal intelligence — doesn't detect time patterns (spikes at 9PM every Tuesday)
4. Clustering is shallow — one-shot at ingest, no merging/splitting/reclassification
5. No proof of value — can't show "saved 47 minutes" or "detected 3 min before alert"
